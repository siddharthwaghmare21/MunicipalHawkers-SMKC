# Future SMKC ERP Integration Strategy

This document outlines the architecture, data structures, and security considerations required to integrate the standalone `MunicipalHawkers` application with the primary SMKC ERP system in the future. 

**Status:** The current application operates independently. This document serves as a blueprint for eventual integration.

---

## 1. Potential Integration Points

Integration should be achieved via **Secure RESTful APIs** (or gRPC) exposed by the central ERP, rather than direct database-to-database connections. This ensures loose coupling and respects the boundary of both systems.

### Core Touchpoints:
1. **User Authentication & SSO:** Centralized login using the ERP's Identity Provider (IdP) instead of local JWT generation.
2. **Citizen/Hawker Master Data:** Fetching existing citizen demographic details (e.g., Aadhar, property tax records) to auto-fill hawker applications.
3. **Financials & Payment Gateways:** Syncing license fee payments and renewal receipts generated by the `MunicipalHawkers` app into the central ERP's General Ledger.
4. **Unified Reporting:** Exporting daily/monthly Hawker metrics to the central ERP's data warehouse for consolidated municipal reporting.

---

## 2. Authentication Requirements

- **OAuth 2.0 / OpenID Connect:** The ERP should act as the authorization server. `MunicipalHawkers` will act as a client.
- **Backend-to-Backend Security:** Any automated synchronization tasks (e.g., nightly batch syncs) must use Client Credentials flow (Client ID & Client Secret) or mutual TLS (mTLS).
- **Token Exchange:** The current local JWT system will be deprecated in favor of verifying JWTs signed by the central ERP's private key.

---

## 3. Data Mapping & Synchronization Strategy

### Hawker ID Mapping
- **SMKC ERP ID:** The central ERP likely tracks citizens using a global `CitizenID` or `PropertyOwnerID`.
- **MunicipalHawkers Mapping:** We will add an `ExternalErpId` (Nullable String) to the `Hawkers` table.
- **Workflow:** When a hawker is registered, a lookup API will query the ERP. If a match is found, the `ExternalErpId` is linked. 

### License Mapping
- **SMKC ERP Ledger:** Financial transactions for licenses will require a mapping. 
- **MunicipalHawkers Mapping:** We will add an `ErpReceiptNumber` to the `LicenseRenewals` table to track the financial receipt generated by the central ERP upon fee payment.

### User/Department Mapping
- **SMKC ERP Users:** The central ERP holds the master list of municipal employees.
- **MunicipalHawkers Mapping:** The local `IT_ADMIN` and `DEPARTMENT_ADMIN` roles will be mapped to global ERP roles (e.g., `ERP_GROUP_HAWKER_ADMIN`). User accounts will be provisioned "Just-In-Time" upon their first successful SSO login.

---

## 4. Required API Contracts (Draft)

To facilitate this integration, the Central ERP team will need to provide the following endpoints:

1. **`GET /api/erp/citizens/{id}`** 
   - *Purpose:* Fetch citizen details to validate Hawker identity.
2. **`POST /api/erp/finance/receipts`**
   - *Purpose:* Post a license payment record to the central ledger.
   - *Payload:* `Amount`, `PayerName`, `DepartmentCode`, `Description`.
3. **`POST /api/erp/sync/hawkers`**
   - *Purpose:* Webhook or batch endpoint to push newly approved hawkers to the ERP for cross-departmental visibility.

---

## 5. Synchronization & Conflict Resolution

### Synchronization Strategy
- **Real-time (Synchronous):** Authentication, fetching Citizen data during registration, and submitting payment receipts.
- **Batch (Asynchronous):** Nightly sync of Master Reports and audit logs to the central ERP data warehouse. 
- **Event-Driven:** Utilizing a message broker (e.g., RabbitMQ, Kafka) where `MunicipalHawkers` publishes events (e.g., `HawkerApproved`, `LicenseRenewed`) that the ERP subscribes to.

### Conflict Resolution
- **System of Record:** The Central ERP remains the absolute Source of Truth for Financials and Citizen Identity. `MunicipalHawkers` remains the Source of Truth for Hawker Licenses and Zone placements.
- **Conflict Handling:** If a record is updated simultaneously, the system of record wins. A "Last Write Wins" approach will be used based on UTC timestamps for non-critical fields.

---

## 6. Error Handling & Fallbacks

- **Circuit Breaker Pattern:** If the central ERP API goes down, `MunicipalHawkers` must not crash. It should fail gracefully, allowing hawkers to be saved locally in a "Pending Sync" status.
- **Retry Mechanism:** Implement an exponential backoff retry strategy (e.g., using Polly in .NET) for failed HTTP requests to the ERP.
- **Dead Letter Queue (DLQ):** Failed asynchronous sync events must be stored in a DLQ for manual review by the IT Admin.

---

## 7. Security Considerations

- **Data Privacy:** Sensitive citizen data fetched from the ERP must not be duplicated or cached longer than necessary in the `MunicipalHawkers` database to comply with local data protection regulations.
- **API Rate Limiting:** Both systems must implement rate limiting to prevent DoS (Denial of Service) during batch syncs.
- **Network Isolation:** Backend-to-backend communication should occur over a secure internal VPC (Virtual Private Cloud) or VPN, not over the public internet.
